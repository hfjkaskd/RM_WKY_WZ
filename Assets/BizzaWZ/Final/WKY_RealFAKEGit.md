执行阶段：[准备工程 / 提交结果]

框架来源：[本地绝对路径或 Git 链接；准备阶段填写]

工作工程路径：[提交阶段填写；准备阶段可留空]
远端项目下载目录：[可选，默认当前工作目录]

【职责与边界】

1. 本任务只负责：识别本地或远端来源、准备本地工程、关联结果 Git、建立基线、提交和推送。
2. 不修改玩法、SDK、Unity 场景、资源、宏或发行配置；不启动 Unity、不执行接入、编译或打包。
3. 可以处理必要的 Git 元数据、Unity 忽略规则和 Git LFS 配置；不得借此修改业务内容、批量转换资源或重写提交历史。
4. 原游戏本地工程只读；框架和原游戏的来源远端只读。提交和推送只能进入指定的结果 Git。
5. 不强推、不清空目录、不丢弃本地修改、不覆盖远端历史。遇到权限、目录、分支或历史冲突，无法安全处理时报告并等待确认。
6. 本提示词已授权当前阶段必要的拉取、关联、提交和推送，无需逐步重复询问。阶段完成后停止，不自动执行其他阶段。

【阶段一：准备工程】

仅当执行阶段为“准备工程”时执行。

一、识别并准备两个项目

分别判断框架来源和原游戏来源是本地路径还是 Git 链接，独立处理：

- 本地框架：直接使用该工程作为工作工程，不重新拉取、不额外复制，以当前本地内容为准，保留已有未提交修改。
- 远端框架：拉取到指定工作工程路径；未指定时，在下载目录下按结果仓库名称创建目录。拉取后的框架就是唯一工作工程，不再复制另一份。
- 本地原游戏：直接作为只读来源，不修改文件或 Git 关联。
- 远端原游戏：单独拉取并保留，作为只读来源，不放入工作工程仓库内部。

因此自动支持：
1. 框架本地，原游戏本地。
2. 框架远端，原游戏本地。
3. 框架本地，原游戏远端。
4. 框架远端，原游戏远端。

检查仓库根目录和 Unity 工程根目录，避免把父目录中的其他项目纳入提交。
目标目录已有内容时先识别，不覆盖、不重新克隆到其中。
本地工程不因准备工作而自动 pull、切换版本或回退修改。
按需获取远端项目的 Git LFS 文件和子模块，确认没有缺失的资源占位文件。

二、关联结果仓库

- 工作工程已有 Git：保留现有历史与本地修改，仅将 origin 关联到结果 Git。
- 工作工程没有 Git：确认工程范围后，在正确目录初始化 Git。
- 记录原远端、当前分支及准备前状态。
- 核实 origin 的 fetch、push 地址及实际推送目标都指向结果 Git；使用 LFS 时也核实其上传目标。
- 不向任何来源仓库或来源子模块推送。
- 结果 Git 不得误用只读来源仓库。结果仓库已有不兼容历史时，不强推覆盖，先报告。

三、建立原始基线

将工作工程当前的框架状态提交并推送到结果 Git，提交说明为：

“框架原始版本”

本地框架已有的修改属于当前基线，应保留，不得先还原成远端版本。
没有文件变更时，可创建空提交作为基线标记，不得为了提交而修改业务文件。
保留必要代码、资源、.meta 和工程配置；不提交 Library、Temp、Logs、obj、临时缓存或本机凭据。
遵循并检查现有忽略规则，避免漏掉必要资源，也不要粗暴覆盖已有规则。

准备成功后，仅报告：
- 工作仓库绝对路径。
- 目标框架 Unity 工程绝对路径。
- 原游戏 Unity 工程绝对路径。
- 结果 Git、分支和基线提交 ID。
- 拉取、LFS、子模块及推送是否成功。
- 阻断项。

到此停止，不开始玩法接入。输出的两个 Unity 工程路径供独立的游戏接入任务使用。

【阶段二：提交结果】

仅当执行阶段为“提交结果”时执行，不重新拉取框架或原游戏。

1. 检查指定工作工程的仓库根、当前分支、文件差异和远端状态。
2. 核实推送目标是指定的结果 Git，不是来源仓库；目标不明确或不一致时先报告，不猜测推送位置。
3. 检查待提交范围，包含本次待交付的代码、资源、.meta、工程配置和必要说明，不纳入工程之外的内容、临时缓存或本机凭据。
4. 不为通过提交而修改玩法或 SDK，不自动修复编译问题，不丢弃人工修改。
5. 有待提交变更时创建提交，提交说明为：

“接入游戏版本”

6. 自动推送到结果 Git 的目标分支，并核实远端提交 ID 与本地一致。
7. 没有文件变更但存在待推送提交时，仅推送；已经同步时直接报告，不制造重复提交。
8. 遇到非快进、历史冲突、权限或 LFS 上传问题时，不强推、不擅自合并或回退，报告具体阻断。

完成后简要报告：
- 工作工程路径、结果 Git 和分支。
- 提交 ID、提交内容摘要及推送结果。
- 是否仍有未提交或未推送内容。
- 阻断项。

Git 提交成功只表示代码已上传，不代表玩法验收通过；不要代替游戏接入任务判断功能是否可交付。
